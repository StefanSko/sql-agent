First, name the layers.

“MCP v2” is useful shorthand, but it conflates an SDK release with a date-versioned wire specification. Keeping the names separate makes migration claims testable.

wire contractMCP protocol 2026-07-28

The modern, sessionless protocol revision. Earlier revisions through 2025-11-25 use the initialize handshake and a connection-scoped session.

Python implementationMCP Python SDK v2 + FastMCP 4

SDK v2 implements the modern protocol. FastMCP 4 builds on it and serves modern and legacy clients from the same server.

Two ways to begin.

The old era negotiates once and keeps connection context. The modern era discovers support, then makes each operation self-describing and independently serviceable.

What actually changed?

Sessionless does not mean featureless. It relocates continuity from an implicit transport session into explicit requests, result cycles, stores, and extensions.

Context moved into the request.

These envelopes are intentionally abbreviated. The important difference is ownership: legacy setup establishes context; modern calls carry it.

Legacy initialization

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "capabilities": { ... },
    "clientInfo": { ... }
  }
}

// Later tool calls use the negotiated session.
One setup exchange gives later messages their protocol meaning.

Modern tool operation

{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "run_query",
    "arguments": { "sql": "SELECT ..." },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion":
        "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities":
        { ... }
    }
  }
}
Each request carries enough context to be dispatched independently.

The architectural truthStateless MCP is still MCP. Pydantic AI still uses a FastMCP client, discovers tool schemas, dispatches tools/call, and converts results. FastMCP 4 removes session affinity; direct FunctionToolset removes the protocol boundary.

The “bash / skill” idea has three layers.

The February 2026 proposal was Cloudflare’s server-side Code Mode. It belongs to the same progressive-disclosure family as CLI exploration and Agent Skills, but they solve different problems and can still retain MCP underneath.

capability compression

Code Mode

Expose fixed search(code) and execute(code) tools. Generated code explores a large typed API and filters intermediate data inside a locked-down isolate. Cloudflare reduced 2,500+ endpoint definitions to roughly 1,000 fixed tokens. Server-side Code Mode is still an MCP server.

procedural disclosure

CLI + Agent Skills

A small skill catalog is always visible; the matching SKILL.md, references, and scripts load on demand. A self-documenting CLI reveals commands through --help. Skills are instructions and resources—not a transport or execution sandbox. MCPorter can put a CLI in front of MCP, but does not remove MCP internally.

schema disclosure

Deferred tool search

Pydantic AI can transparently mark any FunctionToolset or MCPToolset as .defer_loading(). Supported providers search natively; this Ollama/OpenAI-chat path gets a local search_tools fallback. Only matched schemas become callable.

Do not collapse these into “replace MCP with skills.” Code Mode changes the model-facing API; a CLI changes invocation ergonomics; Skills package reusable know-how; deferred loading hides schemas until discovery. Any of them may sit above direct Python or above MCP.

The security boundaryNever expose unrestricted host bash from this web service. A useful CLI arm needs an allowlisted command runner; a real Code Mode arm needs a resource-bounded isolate with only catalog and db.query bindings. Otherwise context savings buy a much larger exfiltration and command-execution surface.

Which choice fits this app?

The current winner already prefetches a small catalog and exposes only run_query. That makes this almost the opposite of Cloudflare’s 2,500-endpoint case.

Deferred loading

toolset.defer_loading() is the transparent first test when tool count grows. With one visible query tool today, search likely adds a round trip rather than saving context.

future cross-system analyst

Code Mode / Skills

Reconsider when dozens of APIs or large intermediate results enter the app. One always-used SQL skill has no selection benefit, while code execution adds sandbox operations and asks Gemma to write reliable code.

Bounded recommendation: do not implement full Bash or Code Mode for the current product path. Add FunctionToolset as the production candidate; use deferred loading as the smallest transparent ablation; keep Code Mode as a measured future arm, not a claimed optimization.

How to test the third path honestly.

Build adapters behind the same typed database contract and run the existing workload. Do not compare Cloudflare’s published 2,500-endpoint savings directly with this four-tool service.

1
Extract one typed database portMove list_tables, get_catalog, and run_query behind a narrow read-only service reused by every adapter.
2
Establish the direct baselineWrap bound methods in FunctionToolset; preserve descriptions, union results, row caps, timeout, and call tracing.
3
Add transparent deferred discoveryRun the granular direct or MCP toolset through .defer_loading(); record the local search_tools call and newly revealed schemas.
4
Prototype restricted execution—not host BashEither use an allowlisted dbctl runner plus an Agent Skill, or a real isolate with only catalog/query bindings. Treat them as separate arms.
5
Gate on total economicsCompare correctness, safety, model requests, total input tokens, latency, result bytes reaching the model, sandbox startup, and implementation/operations cost.

Safe upgrade path.

Treat the dependency bump as a new experimental arm. Compatibility is promising, but the original verdict remains bounded to FastMCP 3 until equivalent evidence is recorded.
