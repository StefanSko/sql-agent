# Local model parameter sweep, 2026-09-10

Model: `gemma4:12b-it-q4_K_M` on Ollama 0.32.15, Apple M4 Pro 24 GB. Development split
(8 cases), one repetition, temperature 0 unless stated. Records:
`benchmarks/records/tuning-development.json` (one-factor-at-a-time, 11 profiles) and
`benchmarks/records/tuning-development-reasoning.json` (reasoning × output-cap grid).
Regenerate the tables with `uv run sql-agent-tune summarize <records>`.

## Findings

| Axis | Effect | Evidence |
|---|---|---|
| Output cap (`SQL_AGENT_MAX_OUTPUT_TOKENS`) | **Dominant.** 256 → 3/8, 512 → 5/8, 1024 → 6/8, 2048 → 6/8. | At 256 the SQL is cut mid-statement (`syntax error at end of input`). At 512 the expert cohort case loses a query mid-CTE and then cannot fit its 11-row answer into the tool call; 1024 solves it in 96 s. |
| Context length (`num_ctx`) | None between 4096 and 16384. | Largest single request was 2916 tokens (temperature 1.0), 2576 at the 1024 cap. 4096 is enough for this catalog but leaves ~30 % headroom; a wider schema or larger row cap would need 8192. |
| Reasoning (`SQL_AGENT_AGUI_MODEL_THINKING`) | **Unusable** for this model in the agent loop. 2/8 at 512, 3/8 at 1024, 4/8 at 2048. | Failures burn the whole output budget on thinking three times without a tool call. The runaway is prompt-chaotic: the same question terminates in 911 tokens with request ID `probe` and exceeds 2048 with request ID `demo-d04-monthly-volume-0`. Ollama treats `low`/`medium`/`high` identically for Gemma 4. It did solve the two cases that fail at temperature 0, so the capability exists but cannot be relied on. |
| Temperature | 1.0 (the Modelfile default the app inherits today) is slower and less reliable. | Median +36 %, 850 vs 473 output tokens per run, 3.2 vs 2.3 requests, 2 failures. Same 5/8 accuracy but different cases: it fixed the two temperature-0 misses and broke two others. |
| Iteration cap (`request_limit`) | No effect between 3 and 10. | Successful runs use 2 to 3 requests. A cap of 3 converts the expert case's exhausted retries into a request-limit failure ten seconds sooner. |
| Row cap | No effect between 50 and 200. | The model writes aggregating queries; no run returned more than a handful of rows. |
| Statement timeout | No effect between 5 s and 15 s at temperature 0. | Only one run hit the 5 s timeout (a correlated subquery in the expert case), and the model recovered with a better query. |

The two cases that fail at every temperature-0 setting are instruction-following slips, not
parameter effects: `d03` filters with `started_at <= '2025-12-31'` and drops December 31;
`d06` returns the right rows under `prev_trip_id` instead of the requested
`previous_trip_id`. Prompt guidance on date boundaries and exact column naming is the next
lever, not a knob.

## Recommendation

- `SQL_AGENT_MAX_OUTPUT_TOKENS=1024`. Costs nothing on easy cases (the cap only binds when
  needed) and is the only change that raised accuracy.
- Set `temperature` explicitly to 0 in the application's model settings; today production
  inherits the Modelfile default of 1.0 while every benchmark runs at 0.
- Keep thinking off. Keep `num_ctx` at 4096 for this schema; pin it with a derived tag
  (`sqlagent-tune-gemma4-12b-it-q4_K_M:ctx8192`) if the catalog grows.
- Leave the iteration cap, row cap and statement timeout as they are.

## Caveats

- One repetition per profile. Temperature-0 runs reproduced exactly across profiles and
  sessions (identical SQL and token counts), so the axis comparisons are sound, but use
  `--repetitions 3` for anything at temperature 1.0.
- Latency is PGlite plus Ollama on a memory-constrained laptop (9 GB model resident, swap in
  use). Absolute numbers are not production numbers; the deltas are.
- The sweep found and fixed three harness defects on the way: the output cap had never
  reached Ollama (`max_completion_tokens` is ignored), PGlite died after ten failed
  statements, and resuming a checkpoint mislabelled incorrect results as correct. See
  `notes/probelog.md` for the mechanisms.
